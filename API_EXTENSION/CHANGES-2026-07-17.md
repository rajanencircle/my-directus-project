# API Extension Changes — 2026-07-17

## Request

> `directus/extensions/api` provides APIs for the collections and their relations for the
> product `hotels`. Without changing anything in the mapping/grouping of the hotels API,
> create new APIs for the new products `tours`, `excursions`, `vehicles` and `cruises`.
> Use the `directus-dev` MCP server. Do not change anything in Directus — just update the
> extension to provide the new products via API.

**Environment used for schema reads:** `directus-dev` (read-only — no collections, fields,
relations, or items were created/updated/deleted there).
**Environment changed by this work:** none. This is a pure code change inside the git repo
(`directus/extensions/api`), reviewed and approved via plan mode before implementation.

### Context
`directus/extensions/api` currently exposes a REST API (`/api/v1/...`) for the `hotels`
product only, built around a routes → controller → service → transformer file split, plus
a `products` aggregator endpoint that merges product types. A `cruises` route existed only
as a 501 stub, and `products.service.js` hardcoded a `cruise: {total: 0}` placeholder in
its catalog.

Goal: add real, working `/api/v1/tours`, `/api/v1/excursions`, `/api/v1/vehicles`,
`/api/v1/cruises` endpoints (list + detail), following the exact same architecture hotels
uses — without changing anything in the hotels mapping/grouping/files, and without
touching the live Directus schema on any environment.

### Non-negotiables
- Do not modify `hotels.*`, `hotel.transformer.js`, or any hotels file/logic/output shape.
- Do not create/update/delete anything in Directus (any environment).
- New product types get their own fully-separate file sets, mirroring hotels' split — no
  shared "product config registry" abstraction, since hotels doesn't have one either.

### Confirmed schema facts (read via directus-dev MCP)
- PK types: tours, excursions, cruises, vehicles are all **integer** (unlike hotels' UUID).
- **tours**: no flat `from_price` anywhere; pricing only has `buy_price` (`tours_prices`),
  no sell-price field/junction wired. Translation junctions: descriptions, price_infos,
  programme, image_badge, price_calculation, surcharges_calculation, specials. Structural
  children: categories, dates, prices, price_periods, occupancies, surcharges.
- **excursions**: `excursions_surcharges` (alias `surcharges_items`) has a real FK back to
  excursions + its own translations junction — same shape as hotels' surcharges. Real
  sell-price junction (`excursions_prices_translations`) exists, so `from_price` is
  genuinely computable.
- **cruises**: `cruises_price_infos_translations.surcharges` is plain free text — no
  structured surcharges collection exists at all. `cruises_price_calculation` turned out
  to be a single per-market pricing-settings row (like hotels' `hotel_prices`) with a real
  flat `from_price` field, **not** a per-cabin/date price matrix — there is no
  cross-product pricing table for cabins × dates × occupancies.
- **vehicles**: confirmed via `relations` reads that `vehicles_prices` has zero relations,
  and `vehicles_surcharges`'s o2m alias actually lives on `rental_companies`, not
  `vehicles`. No FK path exists to query vehicle-level pricing/surcharges. Master
  data/descriptions/media/image-badge are fully wired.

### Implementation plan
0. Fix `HTTP_STATUS.NOT_IMPLEMENTED` missing constant (pre-existing latent bug).
1. Add `utils/grouping.js` — generic, parameterized version of hotels' `groupPrices`,
   additive only (`utils/prices.js` untouched).
2. Per-product file sets under `src/api/v1/<product>/` mirroring hotels' split exactly
   (routes/controller/service/fields/filters/validation + transformer + strip-fields map).
3. Wire into `api/index.js`, `product.transformer.js`, `products.service.js`.
4. Add OpenAPI spec entries, replacing the cruises 501 stub.

### Verification plan
Build the extension; hit new + existing endpoints; diff hotels responses before/after;
confirm catalog counts are real; spot-check computed `from_price` values.

## What was actually built

### 0. Bug fix
- `src/api/shared/constants.js` — added `HTTP_STATUS.NOT_IMPLEMENTED: 501` and
  `HTTP_MESSAGE[501]`. The old cruises stub called `res.status(HTTP_STATUS.NOT_IMPLEMENTED)`
  which was `res.status(undefined)` — a live bug, now moot since cruises no longer 501s.

### 1. New shared utility
- `src/utils/grouping.js` (new) — `groupPrices2(...)`, a parameterized generalization of
  hotels' `groupPrices`. `src/utils/prices.js` (hotels') is untouched.

### 2. Per-product implementations
For **tours**, **excursions**, **cruises**, **vehicles**, added under
`src/api/v1/<product>/`: `.routes.js`, `.controller.js`, `.service.js`, `.fields.js`,
`.filters.js`, `.validation.js`, plus `src/transformers/<product>.transformer.js` and
`src/maps/<product>.strip-fields.js`.

**Deviation from plan:** per-product `*.field-map.js` files were **not** created. Reading
`hotel.field-map.js` at implementation time showed it's dead code — never imported
anywhere except by itself — so replicating that unused pattern across 4 more products
would just be cruft. `strip-fields.js` *is* used (via `stripFields()` in the list-item
transformer) so that one was kept.

Product-specific outcomes:
- **tours** (`/api/v1/tours`, `/api/v1/tours/{id}`) — categories/prices grouped via
  `groupPrices2`. `sell`/`from_price` are always `null` with an inline code comment
  explaining why (no sell-price source in the schema). Surcharges fetched via a separate
  query (same anti-nested-translation-bug pattern as hotels); `tours_surcharges` has no
  status/publish-window fields, so no publication filter is applied there (unlike hotels).
- **excursions** (`/api/v1/excursions`, `/api/v1/excursions/{id}`) — full pricing
  (`groupPrices2` with a real sell-price translations key) and a genuinely computed
  `from_price`. Surcharges fetched separately, filtered by status + publish window
  (`excursions_surcharges` *does* have those fields, unlike tours').
- **cruises** (`/api/v1/cruises`, `/api/v1/cruises/{id}`) — the old 501 stub
  (`cruises.controller.js`/`.routes.js`/`cruise.transformer.js`) was replaced with a full
  list+detail implementation. Because `cruises_price_calculation` turned out to be a
  single settings row with a real `from_price` field (not a matrix), `groupPrices2` isn't
  used here — `cabin_categories`/`price_dates`/`occupancies` are exposed as plain reference
  lists, and pricing comes from `price_settings`/`from_price` directly. No `surcharges` key
  is emitted (the schema has none); the free-text field is surfaced as
  `price_info_translations.surcharges_text` with an explanatory comment.
- **vehicles** (`/api/v1/vehicles`, `/api/v1/vehicles/{id}`) — master data, descriptions,
  media, and image badge are fully populated. `pricing` is always
  `{ available: false, reason: "..." }` with a `// TODO(vehicles-pricing):` comment,
  since no FK exists from the pricing/surcharge collections back to `vehicles`.

### 3. Wiring
- `src/api/index.js` — mounted `setupToursRoutes`/`setupExcursionsRoutes`/
  `setupVehiclesRoutes`; `setupCruisesRoutes` now receives `context` (needed for its real
  service, matching hotels' signature — previously it took none).
- `src/transformers/product.transformer.js` — added `case "tour"`/`"excursion"`/
  `"vehicle"`; `case "cruise"` now calls `shapeCruiseDetail` instead of the old pass-through
  `shapeCruise`.
- `src/api/v1/products/products.service.js` — rewritten to fan out across all 5
  collections. **Deviation from plan:** rather than paginating each collection at the DB
  level and only merging page-sized slices, each type's *entire* published set is fetched
  (`limit: -1`) per request, tagged with `_productType`, concatenated, sorted by
  `date_updated`, and then paginated in memory. This was necessary because merging 5
  independently-paginated queries into one correct global page/sort order isn't otherwise
  possible without a much larger rework (e.g. a UNION view). Flagged here as a genuine
  scalability trade-off worth revisiting if product counts grow large — today it's fine at
  current data volumes. The hotel-specific filter params (`search`, `country`,
  `hotel_group`, etc.) are still scoped to the hotels branch only, as planned; the other 4
  types are filtered only by publish status + `updated_after`. `getProductCatalog()` now
  returns real per-type counts for all 5 types instead of the old hardcoded
  `cruise: {total: 0}` stub.

### 4. Docs updated
- `src/api/v1/docs/openapi.spec.js` — added path entries for `/api/v1/tours`,
  `/api/v1/excursions`, `/api/v1/vehicles` (list + detail), replaced the 501-only cruises
  stub entry with real list + detail entries, added 3 new tags, and updated the
  `/api/v1/products` catalog example payload to show all 5 types. No fabricated "captured"
  example response bodies were added for the new products (unlike hotels' `REAL_HOTEL`
  example) — descriptions call out the real schema gaps (null tours pricing, cruises'
  free-text surcharges, vehicles' pricing stub) instead of inventing sample data.
- `BOTG-API.postman_collection.json` — added `Tours`, `Excursions`, `Vehicles` folders
  (List + Detail requests, same query-parameter style as the existing Hotels folder) and
  replaced the old "List Cruises (not implemented)" single item with a proper
  List + Detail pair. Added new collection variables: `tourId`, `excursionId`, `cruiseId`,
  `vehicleId`.

## Update — 2026-07-21 (cont'd): public `/demo` endpoints

### What was added
A new `GET .../demo` endpoint for each product plus the products aggregator — all
**public, unauthenticated** (no Bearer token required), returning the **first published
item** for that type, shaped exactly like the real authenticated detail endpoint:

- `GET /api/v1/hotels/demo`
- `GET /api/v1/tours/demo`
- `GET /api/v1/excursions/demo`
- `GET /api/v1/cruises/demo`
- `GET /api/v1/vehicles/demo`
- `GET /api/v1/products/demo` — first item across **all** product types (same
  merge/sort as `/products/details`), shaped via the existing product dispatcher

### Implementation
New module `src/api/v1/demo/` (`demo.routes.js`, `demo.controller.js`, `demo.service.js`,
`demo.validation.js`) — added as a standalone module rather than touching any existing
product's `routes.js`/`controller.js` (including hotels', per the "don't modify hotels
files" constraint from the original request). It composes each product's **already
existing, unmodified** `list*`/`get*Details` service functions and `shape*Detail`
transformers — no new query or shaping logic was written; `demo.service.js` just picks
the first id from a `limit: 1` list call, fetches its full detail record, and shapes it.

**Wiring** (`src/api/index.js`): `setupDemoRoutes(router, context)` is called
**before** `router.use(createAuthMiddleware(keyState))` — same placement as the existing
public docs routes — and before the protected per-product route mounts, so Express
matches the static `/demo` path ahead of each product's `/:id` parameter route rather than
that route swallowing it.

### Docs updated
- `openapi.spec.js` — new `Demo` tag + 6 path entries (each with `security: []` to
  document the no-auth-required contract), inserted at the top of `paths` for visibility.
- `BOTG-API.postman_collection.json` — added a `Demo (No Auth)` request as the **first**
  item in each of the Hotels/Tours/Excursions/Cruises/Vehicles/Products folders. Each
  request sets `"auth": {"type": "noauth"}` to explicitly override the collection-level
  Bearer auth, so it works out of the box with no `apiKey` variable set.

### Local testing
Rebuilt, restarted the local container, and tested every `/demo` endpoint with **no
Authorization header at all**:

| Endpoint | Result |
|---|---|
| `/api/v1/hotels/demo` | 200, real hotel data |
| `/api/v1/tours/demo` | 200, real tour data |
| `/api/v1/excursions/demo` | 404 "No demo excursion available" |
| `/api/v1/cruises/demo` | 404 "No demo cruise available" |
| `/api/v1/vehicles/demo` | 200, real vehicle data |
| `/api/v1/products/demo` | 200 (returned a vehicle — most recently updated published record across all types) |

The two 404s are **correct, not bugs** — local's only excursion/cruise test records are
`draft` status, and the demo list query correctly applies the same `status_primarix =
published` filter as the real list endpoints (matches the `/products` catalog's `0`
counts for those two types, confirmed in the previous update).

**One thing worth knowing, not a bug in this code:** sending a request to a `/demo`
endpoint *with* an `Authorization` header containing a bogus value (e.g.
`Bearer totally-wrong-key`) returns `401 Invalid user credentials` — but that rejection
happens inside **Directus core's own platform-level auth**, which validates any
Bearer header against real Directus sessions/static tokens for *every* request
regardless of which extension route it targets, before our router even runs. It is
unrelated to and unaffected by this extension's own `authMiddleware`/`demo` routes. The
actual "no token required" contract is simply to **omit the Authorization header
entirely** — confirmed working above, and exactly what Postman's `noauth` request-level
auth override does.

Regression-checked afterwards: all previously-working authenticated routes
(`/hotels`, `/tours`, `/excursions`, `/cruises`, `/vehicles`, `/products`) still return
200 with the real API key, and `/api/v1/hotels/{id}` without a token still correctly
returns 401 (the demo bypass did not leak into any protected route).
